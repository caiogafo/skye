# Decisions

The choices the owner has made (the log) and those not yet taken (open). Requirements cite them as "D13" or "open decision O7".
A decision is never rewritten: a later one supersedes it and the old one is marked "superseded by Dn". When an open decision is
taken, it moves to the log as the next D-number, the requirement it affects is edited in `10-requirements.md`, and its entry leaves
the open list.

- **O19** Is a separate `gateway` still needed, or does its work become the job of the tools registry? The gateway (Requirements 44 to 48, modelled on Amazon Bedrock AgentCore Gateway: targets, inbound and outbound authorization, policy on every tool call) is an MCP endpoint over a shared catalogue of tools, with a toolset per operation, selection strategies (hybrid search, Jev), scope tokens and the authorizer on every listing and call. The registry in `tools` already holds the capabilities and has a `search`, but that search is not semantic: it scores the name and description with `difflib.SequenceMatcher`, so it is string similarity with no embeddings, and the registry lives in the process and has no external store, targets or authorization. Options: (A) keep both, the registry as the cheap in-process lookup and the gateway as the remote, shared, authorized catalogue; (B) move the catalogue to the registry (external store, targets, selection strategies, toolset per operation, the authorizer check on listing and call, all through Ports in `base`, because `tools` may import only `base` and `auth`, so embeddings arrive as a `VectorEncoderInterface` and the decision model as the `decision` Port) and reduce the gateway to exposing the registry as an MCP server, one thin standard-library adapter; (C) as B, and drop the `gateway` component until someone needs the MCP endpoint, which removes a layer-3 component and Requirements 44 to 48 become milestones of `tools`. To weigh: one catalogue and not two; the layer rules (Requirement 2) and the MCP split (client in `tools`, server in `gateway`, Requirement 10.1); who actually needs a remote endpoint (agents in other processes); the footprint of a registry that grows an external store. If B or C: edit Requirements 44 to 48 and 10.1 first, then the specs of `tools` and `gateway`. Related: O12, O14 to O18, which move with whatever is chosen.
- **O20** Write examples first, for every component, to define the user interface? The examples now run offline against a fake network (`tests/examples`, Requirement 24.3) and running them found seven defects of the library, so they are already the executable statement of how the library is used (`skye.provider` came from one). Proposal: before the design of a component, write the example of how a user calls it, including the extension points and the custom cases: a custom credential source or strategy for `auth`, a custom store backend, a custom provider, a custom tool or exporter, a policy, a memory, a guard, an agent with hooks, a team, a flow. The example fixes the names and the shape of the call, goes in `examples/<component>/`, and is run by the test from the day it is written. Options: (A) example first for every component, then design and tasks from it; (B) example after the implementation, as today; (C) example first only for the extension points (Requirement 6.1). To weigh: each example is small (30 to 80 lines) but fixes the public API early; the example is a test, so changing it later needs a decision line; it gives Kiro a concrete target for design and tasks. If A or C: add a criterion to Requirement 24 and a step to `20-repo.md` ("Creating a new spec": the example comes before the design).
- **O21** *(taken as D34, kept for the history of the options; do not act on it)* Shorter imports through `skye/__init__.py`? Today `import skye` exposes four modules and `provider` (Requirement 7.8), and everyday code needs long paths: `from skye.base.messages import UserMessage`, `from skye.base.completion import CompletionRequest`, `from skye.router import ModelRouter, ModelTarget, RouteConfig`, `from skye.base.interfaces.router import RoutingStrategy`, `from skye.models.registry import ProviderRegistry`, `from skye.tools import capability`. Constraints: `import skye` must load no optional library and stay within the module and cold-start limits (Requirements 7.4 and 7.9, `tests/budget/test_cold_start.py`). Options: (A) lazy top-level names with a module `__getattr__` (PEP 562) in `skye/__init__.py`: `skye.UserMessage`, `skye.ModelRouter`, `skye.capability`, resolved at first use, with an `__all__` and a `TYPE_CHECKING` block so editors and mypy see them; `import skye` stays light; (B) shorter component paths, each component re-exporting its everyday names (`from skye.router import RoutingStrategy`, `from skye.base import UserMessage`) and a minimal top level; (C) leave the explicit paths. To weigh: a short curated list of about fifteen names (messages, request and response, router and its settings, `capability`, `provider`, errors) chosen from the examples, so it follows O20; Requirement 7.8 becomes a list of names, enforced by a test that fails on any name outside it and on a change of the cold-start or module count; collisions and circular imports; the old rule that kept `provider` and the models out of the top level (D28 brought `provider` back as a lazy function). If A: write the list first in Requirement 7.8, then the code and the test, then update the examples to the short form.
- **O23** Budget of the `mcp` extra. The default MCP client is built in (standard library); `fastmcp` is opt-in, so under Requirement 7.10 (budgets are verified on the standard installation) its size should not block CI. Today the extra measures +50.6 MB on Linux against a limit of 48, since PyYAML left the core (D29) and `fastmcp` depends on it. Options: (A) take `mcp` out of the CI gate and report it as known debt in `docs/budgets.md`, keeping the check that `fastmcp` is imported only through the extra (recommended); (B) measure extras over the core plus the extras that declare their shared dependencies; (C) raise the limit to 51 (not wanted). Task: `.kiro/specs/2-services-tools/tasks.md` 6.5, after 6.3 (legacy MCP probes that require `fastmcp` without the extra).
- **O24** The call shape of the model Port (audit finding 25). `ModelInterface.complete(request)` is what the Port says, while every implementation and every example calls `client.complete(messages=[...], model="gpt-4")`; `stream`, `acomplete` and `astream` split the same way, and the base class hides the mismatch with `type: ignore`. Requirement 16.6 says the Port must describe the real call; the question is its exact form. Options: (A) the Port takes `messages`, `model` and options, and also accepts a `CompletionRequest` as the first argument (the shape of the implementations); (B) the Port stays `complete(request)` as the low-level form and `skye.provider` returns a class that adds the `messages=` form, so a function typed `ModelInterface` takes a request only; (C) both Ports, a low-level one and a user-facing one. To weigh: what an extension author writes first; the type-checker with no `ignore`; `Runnable` (Requirement 7.1 says adapters implement it). The typing of `astream` (`AsyncIterator`) and the sync `select_model` of the router Port are defects, not choices, and do not wait for this.
- **O25** Protocol or abstract base class for a Port (finding 28). 20 Ports are abstract base classes, 4 are `@runtime_checkable` `Protocol`s (`AuthenticationInterface`, `AuthorizerInterface`, `DecisionModel`, `Runnable`); an extension author cannot predict whether inheriting is required, and the compliance checker handles only the first kind. Options: (A) `Protocol` for the Ports that third parties implement as plain classes (authentication, authorizer, decision, runnable, observer, safety, memory) and abstract base for the Ports that carry default behaviour (`BaseModelProvider`: retry, health); (B) every Port a `Protocol`; (C) every Port an abstract base. To weigh: `isinstance` and structural typing for the user's own classes; the default behaviour that must be inherited; Requirement 16.7 (one checker for both kinds).
- **O26** An offline demo provider for the examples (findings 1 and 9). Requirement 24.4 asks every example to run with no key and print a result, and today seven of the first examples a newcomer runs end in "skipping". Options: (A) a public module `skye.testing` with a demo provider that answers locally, usable by the examples and by users in their own tests; (B) a helper that lives only in `examples/` and is not part of the package; (C) no provider: each example prints a sample of the output it would give. To weigh: the public surface and the budgets (Requirement 7); a demo provider shipped in the package is a promise; `tests/examples/fake_network.py` already answers every provider in the tests; the pattern `advanced/custom_providers.py` and `providers/bring_your_own_adapter.py` already show with an adapter that echoes.
- **O27** Guessable names (findings 13, 17, 20, 21). Options for each, add an alias or only document the word that exists: `CompletionResponse.text` as a read-only alias of `content` (the first docstring a user reads used it); `CapabilityRegistry.list()` for `list_all`; `skye.provider(name, kind="embedding")` beside `provider_type`; `tool_choice` beside `capability_choice` on the request; `ainvoke` beside `Runnable.invoke`. To weigh: Requirement 22.1 (the library says capability, not tool); every alias is a second spelling to keep (Requirement 22.4); the version is 0.x with no published users, so a rename is cheap now.
- **O28** Public-surface clean-up (findings 19, 16, 23). (a) `skye.router` re-exports six storage backends that live in `skye.store`: keep them documented as an alias, or drop them at 0.1.0 (Requirement 22.4: one home). (b) `MCPClientPort` is the only Port named `*Port`: rename it `MCPClientInterface` (Requirement 22.3) or leave it as a third documented exception. (c) `skye.flows`, `skye.gateway`, `skye.teams`, `skye.policy` import and expose nothing, and `skye.observe` and `skye.guard` have `__all__ = []`: raise a clear `ImportError` ("planned, not available yet") from each, or leave them importable and empty.
- **O29** Unreconciled and overlapping Ports (findings 30, 33, 34). For each of `TokenCounterInterface`, `CostCalculatorInterface`, `ConfigLoaderInterface`, `MultimodalHandlerInterface`, `ErrorHandlerInterface` and `RouteRegistryInterface`, whose implementation does not satisfy them: make the implementation satisfy the Port, change the Port to what exists, or remove the Port from `__all__` until a component needs it (Requirement 16.9). Also: `StorageBackend` and `StorageAdapterInterface` (two storage Ports, the second with no implementation); whether `ModelInterface` extends `Runnable` (Requirement 7.1); and the roles and names of the parts when `ModelRouterInterface` (16 methods) and `PromptBuilderInterface` (22 methods) are split (Requirement 16.9).

- **O30** The outcome of a capability call (tools report, L2, A1). A tool failure is the text `"Error: ..."` inside `CapabilityMessage.content` today, so a tool that legitimately answers `"Error: not found"` cannot be told from a failure, and the agent's consecutive-failure limit (Requirement 42) and the per-error-type policy (O13) cannot be built on it. Options: (A) a `status` field on `CapabilityMessage` with the values ok, error, denied, skipped (the agent hooks already have deny and skip as outcomes), with `is_error` as a derived property; (B) only a boolean `is_error`; (C) the richer `CapabilityResult` returned by the primitive and converted to the message. To weigh: the hook outcomes of Requirement 42; the three result types that exist now (`CapabilityMessage`, `CapabilityResult`, raw); one outcome read the same way on every execution path.
- **O31** The batch execution method, sync or async (tools report, L1). `CompletionResponse.execute_capability_calls` is async only and its name carries no `a`, so a synchronous program (every `complete()` example) must open an event loop for a plain function. Options: (A) make `execute_capability_calls` synchronous and add `aexecute_capability_calls` (the `x`/`ax` rule, Requirement 22.5; the rename is cheap pre-0.1.0); (B) keep it async and add a synchronous `run_capability_calls`. To weigh: the `x`/`ax` rule; the cost of a rename against a published API (none yet); `ExecutableCapabilityCall.execute` is already sync and `registry.execute` already has both.
- **O32** Registration of a decorated capability (tools report, A9, O32). `@capability` returns an object and registers nothing, so the user-facing `create_agent(REACT, capabilities=["search"])` form (a name resolving to a schema) has nothing to resolve against. Options: (A) no implicit global registry; `registry.add(fn)` and `create_agent(capabilities=[fn])` accept objects, names resolve only through a registry the user passes; (B) `@capability(register=True)` into a named registry; (C) an implicit global registry filled by the decorator. To weigh: a hidden global is a surprise and a test-isolation hazard; a name in the agent options must resolve somewhere.
- **O33** One list of calls or two (tools report, L4, O33). `get_capability_calls()` returns executable objects and `capability_calls` plain ones, two lists of one name family holding different types (`ExecutableCapabilityCall`, `CapabilityCall`). Options: (A) one type, `CapabilityCall`, with an `execute()` that uses the capabilities carried by the response; (B) keep two types and rename the second `executable_calls()`. To weigh: one name family; the executable form must not keep a live capability object in a saved `AgentState` (Requirement 42, resumability), so the serialisable call keeps only id, name and arguments.
