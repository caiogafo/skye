# Decisions

The choices the owner has made (the log) and those not yet taken (open). Requirements cite them as "D13" or "open decision O7".
A decision is never rewritten: a later one supersedes it and the old one is marked "superseded by Dn". When an open decision is
taken, it moves to the log as the next D-number, the requirement it affects is edited in `10-requirements.md`, and its entry leaves
the open list.

## Open decisions (not yet taken)
- **O1** The project name (replaces D23): constraints: at most 7 letters, related to air or sky, able to contain the cloud and weather codenames. Candidates seen: welkin, tropos, airmass, mizzle, zenith, aether. When it is decided, the rename is one mechanical task, executed last: the package folder and every import, the classes that carry the old name, the three prefixed environment variables, the configuration file name, the distribution name in `pyproject.toml`, and the occurrences in `budgets.toml`, CI, CODEOWNERS, the Makefile, the specs, the steering, the wiki, the examples and the README; the owner renames the GitHub repository; it is done when `make budget-fast`, `make budget`, `make differential` and the guardrail tests give the same results as before, with the codename test adapted and the old name recorded as the umbrella watermark; `tests/budget/test_no_old_name.py` then fails on any leftover.
- **O2** Trademark check at the registries (USPTO, TMview, WIPO; classes 9 and 42) for the chosen name. Lesson from the dropped name: a web search alone found conflicts (an AI sales-automation company claiming the same marks, a funded AI app, an open-source agent orchestrator), so the registry search comes before reserving the PyPI name.
- **O4** Moving the core models from pydantic to dataclasses, and when.
- ~~**O5** `tiktoken`: keep, drop, or make pluggable.~~ Taken as **D25** (optional `tiktoken` extra, lazy; stdlib approximate counter in core).
- **O6** Where `base/http.py` goes, given that `base` must do no I/O; and whether cloud secret managers are in scope of `auth`.
- ~~**O7** Where MCP resources live; whether the MCP prompt facet implements `PromptBuilderInterface`.~~ Taken as **D26** (resource Port in `base` implemented by the MCP client; prompt facet returns `base` messages, not `PromptBuilderInterface`).
- **O8** Whether decision models (Jev) get their own milestone in `models` and a selector in `gateway`.
- **O9** Policy: the text syntax in the first release (or JSON and TOML first), how much of the Cedar grammar, how closely Cedar compatibility is promised, and whether an official conformance suite is available and under which licence.
- **O10** Policy: how principals map from IAM roles and JWT claims (one fixed way, or defined by each application), the policy-set cache lifetime and the evaluation time limit.
- **O11** Agents: the names `BaseAgent` and `Agent` and whether the operation list misses anything (for example a streaming-chunk hook); streaming hooks on each chunk or only on the complete response; the defaults for retry limit, hook time limit, maximum steps and consecutive failure limit; the budget values.
- **O12** Agents and gateway: who writes the operation description (the agent, the calling application, or the gateway from the conversation).
- **O13** Agents: whether a tool failure goes back to the model by default or stops the run, per error type; whether checkpointing is on by default in Lambda or opt-in.
- **O14** Gateway: which MCP specification version to target and whether responses stream.
- **O15** Gateway: the registry store, DynamoDB only or also S3 or Parameter Store.
- **O16** Gateway: the default and maximum toolset size, and the budget values.
- **O17** Gateway: scope-token key management and rotation.
- **O18** Gateway: JWT signature verification in the gateway itself (RSA without a compiled library), and whether the gateway also fronts model calls (the router) or only tools.
- **O19** Is a separate `gateway` still needed, or does its work become the job of the tools registry? The gateway (Requirements 44 to 48, modelled on Amazon Bedrock AgentCore Gateway: targets, inbound and outbound authorization, policy on every tool call) is an MCP endpoint over a shared catalogue of tools, with a toolset per operation, selection strategies (hybrid search, Jev), scope tokens and the authorizer on every listing and call. The registry in `tools` already holds the capabilities and has a `search`, but that search is not semantic: it scores the name and description with `difflib.SequenceMatcher`, so it is string similarity with no embeddings, and the registry lives in the process and has no external store, targets or authorization. Options: (A) keep both, the registry as the cheap in-process lookup and the gateway as the remote, shared, authorized catalogue; (B) move the catalogue to the registry (external store, targets, selection strategies, toolset per operation, the authorizer check on listing and call, all through Ports in `base`, because `tools` may import only `base` and `auth`, so embeddings arrive as a `VectorEncoderInterface` and the decision model as the `decision` Port) and reduce the gateway to exposing the registry as an MCP server, one thin standard-library adapter; (C) as B, and drop the `gateway` component until someone needs the MCP endpoint, which removes a layer-3 component and Requirements 44 to 48 become milestones of `tools`. To weigh: one catalogue and not two; the layer rules (Requirement 2) and the MCP split (client in `tools`, server in `gateway`, Requirement 10.1); who actually needs a remote endpoint (agents in other processes); the footprint of a registry that grows an external store. If B or C: edit Requirements 44 to 48 and 10.1 first, then the specs of `tools` and `gateway`. Related: O12, O14 to O18, which move with whatever is chosen.
- **O20** Write examples first, for every component, to define the user interface? The examples now run offline against a fake network (`tests/examples`, Requirement 24.3) and running them found seven defects of the library, so they are already the executable statement of how the library is used (`skye.provider` came from one). Proposal: before the design of a component, write the example of how a user calls it, including the extension points and the custom cases: a custom credential source or strategy for `auth`, a custom store backend, a custom provider, a custom tool or exporter, a policy, a memory, a guard, an agent with hooks, a team, a flow. The example fixes the names and the shape of the call, goes in `examples/<component>/`, and is run by the test from the day it is written. Options: (A) example first for every component, then design and tasks from it; (B) example after the implementation, as today; (C) example first only for the extension points (Requirement 6.1). To weigh: each example is small (30 to 80 lines) but fixes the public API early; the example is a test, so changing it later needs a decision line; it gives Kiro a concrete target for design and tasks. If A or C: add a criterion to Requirement 24 and a step to `20-repo.md` ("Creating a new spec": the example comes before the design).
- **O21** Shorter imports through `skye/__init__.py`? Today `import skye` exposes four modules and `provider` (Requirement 7.8), and everyday code needs long paths: `from skye.base.messages import UserMessage`, `from skye.base.completion import CompletionRequest`, `from skye.router import ModelRouter, ModelTarget, RouteConfig`, `from skye.base.interfaces.router import RoutingStrategy`, `from skye.models.registry import ProviderRegistry`, `from skye.tools import capability`. Constraints: `import skye` must load no optional library and stay within the module and cold-start limits (Requirements 7.4 and 7.9, `tests/budget/test_cold_start.py`). Options: (A) lazy top-level names with a module `__getattr__` (PEP 562) in `skye/__init__.py`: `skye.UserMessage`, `skye.ModelRouter`, `skye.capability`, resolved at first use, with an `__all__` and a `TYPE_CHECKING` block so editors and mypy see them; `import skye` stays light; (B) shorter component paths, each component re-exporting its everyday names (`from skye.router import RoutingStrategy`, `from skye.base import UserMessage`) and a minimal top level; (C) leave the explicit paths. To weigh: a short curated list of about fifteen names (messages, request and response, router and its settings, `capability`, `provider`, errors) chosen from the examples, so it follows O20; Requirement 7.8 becomes a list of names, enforced by a test that fails on any name outside it and on a change of the cold-start or module count; collisions and circular imports; the old rule that kept `provider` and the models out of the top level (D28 brought `provider` back as a lazy function). If A: write the list first in Requirement 7.8, then the code and the test, then update the examples to the short form.
- **O22** Rename or remove the extra `openai`. It declares only `tiktoken`, for exact token counts of `gpt-*`, `o1-*` and `o3-*`; it does not install the OpenAI SDK, because OpenAI is served by the built-in REST adapter, so the name says the opposite of what it does (Requirement 7.13). Options: (A) rename it for its function (`tokens`), keeping `tiktoken` lazy and optional (decision D25), with its own budget entry under the new name; (B) remove the extra and let the user install `tiktoken` themselves, the library using it when it is importable and the standard-library estimate otherwise (the declared-extra check then needs `tiktoken` listed somewhere); (C) drop `tiktoken` and add `TokenCounter.register_tokenizer` (the option 3 of the former O5). To weigh: `tiktoken` is compiled (3 compiled distributions, +8.4 MB on Linux) and downloads its vocabulary on first use, a cost in serverless; the extras `anthropic`, `bedrock`, `cohere`, `google` are empty and exist only so that old install commands keep working.
- **O23** Budget of the `mcp` extra. The default MCP client is built in (standard library); `fastmcp` is opt-in, so under Requirement 7.10 (budgets are verified on the standard installation) its size should not block CI. Today the extra measures +50.6 MB on Linux against a limit of 48, since PyYAML left the core (D29) and `fastmcp` depends on it. Options: (A) take `mcp` out of the CI gate and report it as known debt in `docs/budgets.md`, keeping the check that `fastmcp` is imported only through the extra (recommended); (B) measure extras over the core plus the extras that declare their shared dependencies; (C) raise the limit to 51 (not wanted). Task: `.kiro/specs/2-services-tools/tasks.md` 6.5, after 6.3 (legacy MCP probes that require `fastmcp` without the extra).
